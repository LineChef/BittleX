AI Head Hybrid Plan

The head becomes G2's microphone, speaker and face. A small fork of its firmware lets the Pi start the head's conversation by command, play G2's own voice through it, and later receive its microphone so the Pi's own mic and speaker can go. Conversation uses the head's free cloud model, which reaches G2 through tools on the Pi. There is no backend. Nothing is built past the tool-server proof. The head adds overhead and limits, so it has to be worth it: the reason for it is removing the Pi's own mic and speaker, and the first step, whenever you say go, is a spike that tests exactly that.

What Petoi confirmed (2026-10-15)

  • Head firmware is a Petoi fork of xiaozhi-esp32 (Quaddle board, robot UART, MCP, prompts). Public repo and release expected in about two weeks. Builds with ESP-IDF 5.5.x (they use 5.5.4).
  • The head checks an OTA URL (compile-time default CONFIG_OTA_URL, overridable in NVS as ota_url). The JSON it returns can write WebSocket or MQTT settings to NVS, so sessions can be redirected to another server after provisioning without reflashing. Petoi disabled OTA sync by default.
  • On-device tools use MCP (JSON-RPC 2.0, tools/list and tools/call) over the session. Extra model tools are normally added on the server side (xiaozhi-esp32-server). Whether the xiaozhi.me Extensions tab attaches a tool server is not documented in the firmware.
  • xiaozhi.me: Qwen real-time for personal accounts; no stable public developer API; an account needs a phone number for an SMS code.
  • Host-audio mode (head mic and speaker driven by a host) is not a product feature. It means extending AudioService and WebsocketProtocol or MqttProtocol (Opus in and out, docs/websocket.md).
  • Wake words: a fixed set of pre-trained ones.
  • Motion UART output has no user setting; it is sent when MCP, voice or gamepad issues a command (self.robot.send_command). UART pins are fixed in second_uart.h; changing them needs a board port and rebuild.
  • The BiBoard's onboard voice command module can be disconnected and its port given to the head, so the head does not share UART2 with the Pi. The head can draw 5 V from the BiBoard.
  • No Grove Vision AI V2 tool in the head firmware and none planned (may need an ESP32-S3). Enabling the head's camera demo disables its IMU.
  • Motion firmware: gb disables the balance reflex, gu turns the gyro off. A timer in the motion firmware can rest G2 when the UART is silent for a set period. The IMU runs faster without value printing; angular rate is available as an intermediate value. Back touch pads can be given other triggers.

What you get

  • Hands-free "G2", no button hardware (F0).
  • G2's own voice and speech on his own initiative (F1).
  • The Pi's microphone and speaker removed, after the gate (F2).
  • The free model kept; fewer Claude calls.
  • No server to run.

What it gives up

  • One voice during conversation: the free model speaks in a stock voice.
  • Claude's quality in conversation; memory arrives in small pieces by tool.
  • Conversation audio staying in the house.
  • Independence from XiaoZhi's free tier.
  • A custom wake word on the head and talking over him (C3 limits).

What you could end up with

  • A, the full hybrid: the Pi's mic and speaker removed, hands-free, free model, memory. About 40-45%.
  • B, the backup: speaker removed, a small mic kept. About 60%.
  • C: hands-free, free model and memory, Pi audio unchanged. About 70-75%.

Judgment estimates, revised after the spike. If full mic removal cannot work, stop and reassess whether the head is worth continuing.

The tests that decide things

  1. Capacity and mic quality (the spike)
  2. Activation of a self-built firmware (the spike's first half)
  3. Recall-tool call rate (phase 0)
  4. Head current and mass (phases 1 and 3)
  5. Loudness (phase 4)
  6. Servo noise at the mic (phase 5)

A failure changes what comes next, not what came before.

Fallbacks and rollback

  • Every firmware phase rolls back to the flash backup (private, on the Mac).
  • If F0 fails: the button by one wire or an outside pusher.
  • If F2 fails: stay on phases 0 to 4 with the Pi's mic.
  • Partial removal (the speaker only) is the backup if the mic cannot go.
